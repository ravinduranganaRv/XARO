# XARO security review (existing store + Studio)

Scope: the static store on GitHub Pages, its browser-only admin, the Apps Script order receiver, and the Studio / rug-maker workspace that talks to Supabase. Nothing here changes how the store looks.

Status words: **FIXED** (changed and tested), **MITIGATED** (risk reduced, not removed), **OPEN – needs owner decision**.

| # | Finding | Status | What was done / what is needed |
|---|---------|--------|--------------------------------|
| 1 | No Content-Security-Policy; any injected script could run and send data anywhere | **FIXED** | `build.py` writes a CSP meta tag. Every inline script is pinned by SHA-256 (no `unsafe-inline` for scripts), `connect-src` allows only Supabase and Google Apps Script, `object-src 'none'`, `base-uri 'self'`. Tests: `tests/security.test.js` (hashes always match the built page), `tests/e2e/csp_flow.py` (store, Studio, 3D, admin sign-in, assistant load with zero violations). Header-only rules (`frame-ancestors`, HSTS) cannot be set on GitHub Pages. |
| 2 | Stored data rendered as HTML: product image address and SKU were placed in HTML unescaped | **FIXED** | Image addresses are accepted only if `https:` or an embedded image with no quote/angle characters; SKU attributes escaped. Test: `tests/e2e/xss_flow.py` fills every free-text field of every stored record (customers, orders, quotes, chat, designs, products, settings, admins) with attribute-breaking markup and walks the store and every admin tab: 0 injected elements. |
| 3 | Rug-maker workspace screens could render hostile text from the database | **PASSED** (MOCK backend) | `tests/e2e/xss_workspace.py`: hostile names/notes in yarns, projects, quotes, orders, designs, business profile – 0 injected elements on all 14 screens. |
| 4 | Customer details could be sent to any https address typed into the admin "sync" setting | **FIXED** | Only `https://script.google.com/macros/s/<id>/exec` (or the `/a/macros/<domain>/s/<id>/exec` form) is accepted, in the settings screen and again at send time. Unit-tested. |
| 5 | Password hashing strength for admin accounts created later | **FIXED** | New and changed admin passwords use PBKDF2-SHA256 with 310,000 iterations (was 120,000). Existing hashes keep working (iteration count is stored per account). |
| 6 | Secrets in the repository or history | **PASSED** | History scanned for Stripe/Supabase service keys, JWTs, private keys, GitHub/AWS tokens: only the Supabase *publishable* key (public by design; row-level security protects data) and test fixtures. CI also scans every push. |
| 7 | Spreadsheet formula injection through the Apps Script receiver | **PASSED** | `apps_script/Code.gs` already prefixes cells that start with `= + - @`; size limits and a script lock are present. |
| 8 | Studio uploads (SVG/images) | **PASSED** | The existing SVG sanitiser drops scripts, `foreignObject`, event attributes and external references; images are decoded and re-encoded on a canvas. |
| 9 | The store admin is a browser-side lock: the owner's salted PBKDF2 hash ships inside the page and sign-in attempt limits live in the visitor's own browser | **OPEN – needs owner decision** | This was documented design (`docs/BACKEND.md`). It protects against casual visitors only: anyone can download the page and try passwords offline against the hash, and anyone can edit their *own* browser storage. Because orders and customers live in each visitor's browser, there is no shared data for an attacker to read, but the admin password should be treated as guessable-if-weak. **Proper fix:** sign the admin in through Supabase Auth with the role checks already built in the database, and keep products, orders and customers in Supabase. It needs (a) the owner e-mail address to be supplied by the owner, (b) the Supabase "Confirm email" setting kept on, (c) a go-ahead to move the catalogue and orders to Supabase. Until then: use a long, unique admin password (16+ characters) and change it from the admin screen (it is re-hashed at 310,000 iterations). |
| 10 | Customer names, e-mails, phone numbers and orders are stored unencrypted in the browser's local storage | **MITIGATED** | Unavoidable for a serverless store; data never leaves the browser except through the Apps Script address the owner configures (now locked to Google). Do not use the store on a shared computer without choosing "Switch account"/"Reset" in the admin. The Supabase-backed Studio account stores designs under row-level security. |
| 11 | Edge functions (`create-checkout`, `stripe-webhook`, `zaro-chat`) | **OPEN – not deployed** | Written and tested against mocks only (`tests/edge.test.mjs`). Deploying needs the owner to enter the Stripe secret and webhook secret in the Supabase dashboard (never in chat) and to approve any cost. |
| 12 | Clickjacking (page can be framed) | **OPEN – platform limit** | GitHub Pages cannot send `X-Frame-Options`. A frame-busting script was not added because it would break legitimate previews; moving the site behind Cloudflare/Netlify headers would fix it. |

## Rollback
Every change in this review is in `build.py` (CSP block), `src/store.src.html` (image/SKU hardening), `src/mod/data.js`, `src/mod/admin*.js` (sync address, iteration count). Reverting the commit and running `python3 build.py` restores the previous page exactly.
